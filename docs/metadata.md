# Metadata values

By default, with `ChromaMetadataValues.Exact`:

- strings stay strings;
- lists come back as `List<object>` of `string`, `long`, `double` and `bool`, like single values;
- a `double`, `float` or `decimal` comes back as a `double`, also when it is whole. The client writes `2.0`, as the Python client does, and Chroma keeps it a float.

Values that earlier versions of this client wrote as `2` stay integers in Chroma, so `LessThan("d", 2.2)` does not find them until they are written again.

With `ChromaMetadataValues.Inferred`, as in earlier versions, a string that looks like a date comes back as a `DateTime`, and a list as a `JsonElement`:

```csharp
var options = new ChromaConfigurationOptions(uri: "http://localhost:8000").WithMetadataValues(ChromaMetadataValues.Inferred);
```

A list in metadata, written and filtered:

```csharp
await collectionClient.AddAsync(new ChromaRecords(["a"]) { Embeddings = [new([1f, 0.5f, 0f])], Metadatas = [new Dictionary<string, object> { ["tags"] = new[] { "red", "blue" } }] });
var tagged = await collectionClient.GetAsync(where: ChromaWhereOperator.Contains("tags", "red"));
```

In `UpdateAsync` and `UpsertAsync`, a null value or an empty list deletes the key on every tested Chroma, with the sparse vectors the client computes from its text. The type does not allow null, so write `null!`. A null goes to the record whether it has the key or not: every tested Chroma takes it, also in an upsert that creates the record. So two writes of the same record at the same time leave the record of the one that writes last: when that one deletes a key, the key goes, also if the other one added it. The keys the metadata does not have stay, as in Chroma. A null document keeps the stored one, as in Chroma 1.x and Chroma Cloud, while the 0.x servers delete it ([COMPATIBILITY.md](COMPATIBILITY.md)); with `NullDocumentsDelete = true` in `ChromaRecords` it deletes it, which Chroma 1.x cannot do, so the client writes an empty document to every record whose document goes, without a read. That needs one of three ways to delete documents, on the collection client: `WithDocumentCopyKey(key)` and `WithDocumentDeletionKey(key)` tell the empty document from an empty text and read it back as null, and `WithEmptyDocumentDeletions()` reads it back as an empty string. Without one of them, a null document with `NullDocumentsDelete` throws an `ArgumentException` before any request. A collection client chooses once: the same call again changes nothing, while another of the three methods, or the same one with another key, throws an `InvalidOperationException` that says the way the client has. On Chroma Cloud, which counts a null against its quota of 32 keys, a write with nulls that would take a record beyond the quota throws an `ArgumentException` before it goes, without a read. The count has the keys that the client adds too: the copy of the document, the mark of a deleted document and the BM25 sparse vectors. A record with more than 32 values and no null goes, and Chroma Cloud rejects it with `422` "Quota exceeded". With `WithReadsBeyondKeyQuota()` in the options of the client, the client reads that record first instead, and sends the nulls only to the keys it has, with two risks: a write of another client between the read and the write can keep what it wrote, and when an id comes more than once in the same write, a key that a later occurrence deletes can stay if an earlier one wrote it. `AddAsync` throws an `ArgumentException` for a null value or an empty list: Chroma 0.x would drop the key, and 1.x rejects the request. A record without metadata keys comes back with an empty `Metadata`, which Chroma sends as null; `Metadata` is null when the read does not include the metadatas. An empty metadata is sent as no metadata (null) in `AddAsync`, `UpdateAsync` and `UpsertAsync`, also in batches with other metadatas: every tested Chroma, 0.4.10 to 1.5.9 and Chroma Cloud, treats the two the same, so a new record has no metadata and a stored one keeps its own. The Python client rejects it instead. A list that holds values of more than one type, like a string and a number, throws an `ArgumentException`, as in the Python client: Chroma rejects it with an error that does not say what is wrong. In `ChromaRecords` a record can have null metadata or a null document, and a list of metadata that are all null goes as no metadata.

`WithDocumentCopyKey(key)` of a collection client returns a client of the same collection that copies each document into the metadata key, so that a `where` filter can compare the whole text, which `where_document` cannot. A document deleted with `NullDocumentsDelete` loses its copy, so the client reads an empty document without its copy as null: a document comes back as it was written, empty or null. For that it reads the metadata with the documents, and leaves it out of the results that do not ask for it. The client deletes a document without reading the record first: it writes the empty document and deletes the copy of every record whose document goes, also of one without a document, which comes back as null all the same. A `where_document` filter that matches an empty text sees that record as one with an empty document: on Chroma 1.5.9 `$contains ""` and `$regex "^$"` find it and `$not_regex "^$"` does not, and on Chroma Cloud `$contains ""` finds it. On Chroma Cloud, which takes a metadata value of at most 8,182 bytes, a longer document goes without its copy, and an update or an upsert deletes the copy it had; on a single server every document has its copy. Up to 2.12.0 a second call with another key replaced the key; now it throws an `InvalidOperationException`, while the same key again works as before.

`WithDocumentDeletionKey(key)` of a collection client returns a client of the same collection that marks a document deleted with `NullDocumentsDelete` under the metadata key, instead of copying every document. It writes the empty document with `true` under the key, and any other document that an update or an upsert writes deletes the mark with a null, so no write reads the records first. It reads an empty document with the mark as null, and an empty one without it as an empty string; the mark stays in `Metadata` like any key. For that it reads the metadata with the documents, and leaves it out of the results that do not ask for it. As with the copy, a deletion writes the empty document also to a record without a document, which a `where_document` filter that matches an empty text then sees as one with an empty document. On Chroma Cloud the mark and its null count against the quota of 32 keys.

`WithEmptyDocumentDeletions()` of a collection client returns a client of the same collection that deletes a document with `NullDocumentsDelete` by writing an empty one, without a copy or a mark and without a read: it reads back as an empty string, as the Python client of Chroma reads it. As with the copy, a deletion writes the empty document also to a record without a document, which a `where_document` filter that matches an empty text then sees as one with an empty document.

`ChromaMetadataConvert` converts .NET values to metadata values and back, always in the same form: `ToMetadataValue` writes a `DateTimeOffset` as round-trip text in UTC, so that equal instants are equal text, a `DateTime` as round-trip text with its `Kind`, a `DateOnly` as `yyyy-MM-dd`, and a sequence as a list; null and an empty sequence give null, no value. `FromMetadataValue(value, type)` reads a value of `ChromaMetadataValues.Exact` as the type, also arrays and lists, and throws an `InvalidCastException` for a value that does not convert. A filter with a converted value finds the values converted the same way. `ToMetadata(values)` builds the metadata of a record from keys and .NET values, each converted with `ToMetadataValue`; a value that converts to null stays as null, which deletes the key in `UpdateAsync` and `UpsertAsync`. The client does not convert the values of a metadata dictionary by itself.

[docs/COMPATIBILITY.md](COMPATIBILITY.md) lists the versions that store lists in metadata, and what the client does on the others. The client asks the server for its version once, and only when a record has a list.

Chroma 1.5.0 to 1.5.9 keep the lists of the records of a deleted collection or database, and give them to the next records they store, in any collection (KD-12 in [COMPATIBILITY.md](COMPATIBILITY.md#known-defects-of-the-servers)): delete them with `deleteRecordsFirst: true`, as [Collections and records](collections.md#collections-and-records) says. Every Chroma 1.x reports the same version, so the records go first on all of them.

An existing `ChromaClient`, for example one from dependency injection, gives a client that reads values the other way. That client shares the `HttpClient`, the options and what was learned about the server. `Options` returns the options of a client:

```csharp
var inferred = client.WithMetadataValues(ChromaMetadataValues.Inferred);
Console.WriteLine(inferred.Options.MetadataValues); // Inferred
```

`WithMetadataValues` of a collection client does the same for one collection.
